# Tasks plugin

`@lapis-notes/lapis-plugin-tasks` owns the first-party external Tasks catalog
and plugin runtime. A task is a Markdown file with YAML front
matter. The filesystem is authoritative. AppDatabase owns the public
`tasks/task` projection. The plugin registers a main-area planner view.
Host movable panels remain unspecified.
Reusable leaf controls come from public Design Core APIs.
`ApplicationTaskAreaPicker` is the catalog list picker and composes Design
Core Command View. `ApplicationTaskAtPicker` is the planner `plan.at`
day-part dropdown. The Today surface is a selected-date daily agenda with
configurable clock boundaries. Catalog adaptation keeps YAML `open`, `completed`, and
`canceled` on `Task.status` instead of collapsing canceled into done.
When labels are the date or undated bucket; At labels are the day-part.
A vault MAY include one `task-list-navigation` Markdown
file whose headings are sidebar sections and whose links pin root lists.
Task and task-list files remain arbitrary rich Markdown: H2–H6 headings provide
grouping context and contiguous unordered-list links to typed task documents
provide structural membership and safe sorting boundaries. There are no
reserved Items or Subtasks headings. The
`Plugins/Tasks/Panels` catalog story composes planner navigation, planner
body, and task detail with Design Core Column Canvas. That presentation is
not a host movable-panel runtime.
Selecting a list replaces only the planner body with the complete provider-
mounted Markdown file; the Column Canvas title remains workspace chrome.

This chapter is the package contract and the only normative MUST table. The
following chapters describe the implemented model:

- [Documents](./documents.md): Markdown kinds, heading paths, structural
  entries, and task runs
- [Rolling recurrence](./documents/recurrence.md): repeat schema, completion
  anchors, date advancement, checklist reset, and skip behavior
- [Runtime](./runtime.md): parse, project, query, and mutations
- [Lists](./lists.md): navigation pins, structural parents, and the sidebar
  tree
- [Planner](./planner.md): planner state, Column Canvas composition, daily
  agenda, and shared Task rows

| LN-TASK-011 | CV-only `applicationId`, `linkedTo`, and `JobApplication` shapes MUST stay in catalog model fixtures and MUST NOT become canonical Task resource types. |
| LN-TASK-012 | Package Storybook MUST include a `Plugins/Tasks/Panels` Column Canvas composition of planner navigation, planner body, and closeable task detail without `AppShell`. Additional closeable columns MAY open from the selected task. This catalog canvas MUST consume public Design Core `column-canvas`, MUST fill the Storybook viewport without page-level scrollbars, MUST use the App Shell sidebar surface, MUST render the leading Tasks column without a column border so it blends into that surface, MUST render the sticky Tasks overlay without corner radius, MUST keep the planner column’s start corners complete, MUST render the Tasks resize hover surface inside the adjacent planner body so that body clips it to its start corners, MUST keep a transparent pointer-accessible resize target straddling both sides of the planner’s start border, MUST inset the target’s block edges by the same border width, MUST size the leading Tasks column to the navigation labels and counts, MUST align the Tasks column header with the planner column header, MUST make the planner column collapsible through its header toggle, MUST keep Tasks column hover and selected item states visible on the sidebar surface, MUST mount task detail directly in the detail column without an extra story wrapper, MUST place the Tasks resize handle on the planner column’s start border with no gap between those two columns, and MUST NOT register host movable panels. |
| LN-TASK-013 | `ApplicationTaskAreaPicker` MUST compose `@lapismd/design-core/shadcn/command-view` for the searchable list picker. It MUST NOT use native Command as that picker surface. |
| LN-TASK-014 | A canonical task MUST be a Markdown file whose front matter includes `type: task` and a stable `id`. The display title MUST be the first H1, else the filename. Child files MUST NOT store parent or list ids. |
| LN-TASK-015 | A canonical list MUST be a Markdown file whose front matter includes `type: task-list` and a stable `id`. Its display title MUST use a nonempty top-level front matter `title` when present, otherwise its first H1, otherwise a human-readable form of its stable id (for example, `list-docs` becomes `List Docs`). `list.status` MUST be `active` or `archived`. Lists MUST NOT be completable outcomes. List chips MUST show this display title rather than an available raw list id. |
| LN-TASK-016 | Task planning metadata MUST nest under `task:` with `status` `open`, `completed`, or `canceled`, and `start` `anytime`, `someday`, or a date. Inbox, plan, deadline, repeat, and comments MAY be omitted. When present, `plan.at` MUST be `anytime`, `morning`, `afternoon`, `evening`, or `HH:mm`, and `repeat` MUST follow LN-TASK-044. YAML MUST NOT store `today` or `upcoming` flags or task `plan.at: all-day`. |
| LN-TASK-017 | Task and task-list bodies MUST allow arbitrary Markdown before, between, and after structural entries. No heading text, including `Items`, `Subtasks`, or `Checklist`, MUST have reserved structural meaning. An unordered list item whose complete direct content is one local Markdown link is a structural candidate; ordinary prose links, rich list items, ordered-list items, external links, fragment-only links, and checkbox items MUST remain ordinary Markdown. A checkbox in a task document MUST be a lightweight checklist item wherever it appears; task-list checkboxes MUST remain Markdown-owned content and MUST NOT contribute task progress. |
| LN-TASK-018 | Inbox, Today, Anytime, Upcoming, Someday, Completed, Logbook, and daily Review MUST be derived query-AST wrappers over the public `tasks/task` projection. Completed MUST match only completed tasks; Logbook MUST match completed and canceled tasks. The repository snapshot, navigation counts, and rendered planner MUST use the same injected local clock. Every planner destination MUST render its own derived rows, heading, count, icon, and empty state; Inbox and Review MUST NOT fall through to Logbook presentation. Each named-view navigation count MUST equal the number of Task rows in that view; Today's count MUST equal its open daily-agenda rows and exclude the collapsed Done history. Overdue `plan.date` values MUST stay visible until the user reschedules, completes, skips, or cancels. Upcoming day rows MUST place open tasks by plan date or, when plan is omitted, deadline. Catalog adaptation MUST NOT treat a deadline-only task as undated anytime. |
| LN-TASK-019 | Mutations MUST edit the owning Markdown file, reparse it, and upsert the projection from that parse. Completing or editing a linked child MUST update the child file. A rolling completion with checklist reset MAY change every lightweight checkbox marker in that task document. Structural mutations MUST use guarded source ranges and MUST NOT regenerate the complete Markdown body. |
| LN-TASK-020 | Planner lists and cards MUST consume `TaskSummary` rows from the AppDatabase tasks projection. Detail and editor surfaces MAY load the Markdown `TaskDocument`. UI MUST NOT treat the database as authoritative. |
| LN-TASK-021 | Canonical catalog types MUST use the Markdown-first schema. Catalog planner fixtures MUST round-trip through task documents. Area membership MUST mean an incoming `task-entry` from a `type: task-list` document, independent of heading text or source position. |
| LN-TASK-022 | Package Storybook MUST include `Plugins/Tasks/Shell` desktop and phone-width stories that boot a public `App`, load File Explorer, Search, Markdown, and `TasksPlugin`, seed planner Markdown, and restore a `tasks` leaf in `WorkspaceShell`. Both stories MUST finish their interaction play on the Today daily agenda with all five ordered sections present, the populated checklist progress for Review interview notes visible but collapsed, and the Lapis left sidebar collapsed, so opening the visual story documents the current Tasks surface rather than an intermediate acceptance state. Canvas stories MUST fill the available Storybook viewport. Docs embeds MUST stay height-capped. The live planner MUST use the same pinned clock as the repository snapshot. Show Code MUST use public package imports. |
| LN-TASK-023 | A vault MAY include at most one authoritative Markdown file whose front matter `type` is `task-list-navigation` and whose `id` is stable. Extra navigation documents MUST be ignored after a diagnostic. Headings in that file MUST be presentation sections, not resources. Links under those headings MUST pin root lists. In ordinary Markdown reading and live-preview surfaces, a navigation link resolving to a Task List MUST use the same rich List-row presentation as a `list-entry`, while remaining a presentation-only `navigation-item` with no planner mutation controls. The file MUST remain ordinary vault Markdown and MUST NOT live in plugin data. |
| LN-TASK-024 | Target document type MUST determine the derived relationship: `task` becomes `task-entry`, `task-list` becomes `list-entry`, ordinary links remain `reference`, and navigation-file links become `navigation-item`. Structural ownership across `task-entry` and `list-entry` MUST be singular for both Tasks and Lists. All four source/target combinations MUST be allowed. Repeated occurrences from one source count as one parent, while distinct multiple parents, self-links, and recursive cycles MUST be diagnosed and removed from the active derived graph without changing Markdown. `navigation-item` and `reference` MUST NOT establish structural parenthood. |
| LN-TASK-025 | The planner Lists sidebar MUST render Lists, then expandable navigation-section folders, then pinned root lists, then nested task-lists from outgoing `list-entry` edges. Section folders MUST default expanded. All lists MUST be an expandable section folder for unpinned structural roots. Tasks MUST NOT appear in that tree. Selecting a section MUST NOT filter the planner. Opening a document surface MUST render mixed `task-entry` and `list-entry` rows in Markdown order. |
| LN-TASK-026 | Reordering pinned roots and moving lists between navigation sections MUST rewrite only the navigation Markdown. Nesting, unnesting, deleting, relabeling, and sorting structural entries MUST rewrite only guarded list-item or TaskRun ranges and then reproject; those operations MUST NOT create or depend on a reserved heading. Renaming a list with a front matter `title` MUST update that title and its H1 while structural parent labels are updated in place. Creating a list MUST write a new `task-list` file without inventing an Items section. Archiving MUST set `list.status` to `archived`. Deleting a list MUST unlink structural and navigation parents, remove only the list file, and leave child files. |
| LN-TASK-027 | The Lists tree MUST reuse Design Core Explorer indent-guide tokens and nested-sublist chrome. It MUST support inline rename and HTML5 list-tree drag with auto-expand. List rows MUST offer a Design Core context menu with Open note, Rename, New nested list, Unpin when the list is a pinned root, Archive, and Delete. Navigation-section folders MUST offer Rename except All lists, and New list. It MUST NOT mount `WorkspaceExplorer`. |
| LN-TASK-028 | The Column Canvas first column MUST use the same planner drop-host attributes as the App Shell sidebar so dragging a task over a bucket or list morphs the drag preview and highlights the drop target. |
| LN-TASK-029 | Tasks plugin data MUST be versioned and MAY store only plugin-owned presentation settings. `dayParts.afternoonStartsAt` and `dayParts.eveningStartsAt` MUST be valid ordered local `HH:mm` values and MUST default to `12:00` and `17:00`. `dailyAgenda.hideOverdueTasks` MUST be a persisted boolean defaulting to false. The settings tab MUST expose all three values, reject invalid or unordered day-part edits, serialize saves, migrate absent, version-1, or malformed data to current defaults, and notify open Tasks views after persistence. Day-part changes MUST reclassify only clock-valued `plan.at` rows; the overdue preference MUST change only selected-agenda inclusion. Neither setting MUST rewrite Task Markdown. |
| LN-TASK-030 | The package MUST publicly export `TaskDaySection`, `TaskPlannerDaySnapshot`, `TaskPlannerWeekDay`, and their pure routing and week helpers. The Today planner MUST be a controlled selected-date daily agenda. It MUST default from the injected local clock and present the selected weekday plus uppercase month/year above a Monday-first seven-day selector. That complete calendar header, including previous- and next-week controls, MUST remain sticky within the planner scroll viewport; both week controls MUST remain ghost buttons at rest and show a semantic grey border without an outline ring on hover, while keyboard focus retains its visible ring. The selector MUST distinguish actual today from the selected date and the Column Canvas header action MUST return to today whenever they differ. Selecting another date MUST update both calendar labels and presentation only. By default the selected agenda MUST include open tasks whose plan date or deadline is on or before that date; when `dailyAgenda.hideOverdueTasks` is true it MUST include only tasks whose plan date or deadline matches the selected date, without changing Review. The Today header MUST present the conditional Today shortcut, a task-detail-styled actions menu, and the collapse control in that left-to-right order, with collapse farthest right. The menu MUST provide session-only Hide completed tasks, Mark all incomplete for the selected date, and persisted Hide overdue tasks actions. Mark all incomplete MUST reopen every completed task in the selected date's Done group while preserving its plan. |
| LN-TASK-031 | The daily agenda MUST always present Anytime, Morning, Afternoon, Evening, and Done in that order. Each section header MUST keep its icon and title at the start while placing its item count in the trailing cluster immediately before the disclosure control. Explicit `plan.at` day parts MUST route directly; `HH:mm` MUST route through the configured boundaries; absent or invalid times MUST route to Anytime. The four open sections MUST default expanded, Done MUST default collapsed, every section MUST remain a drop target while empty or collapsed, and disclosure state MUST remain in memory across date changes without being persisted. Tasks-owned colors derived from neutral, warning, info, accent, and success roles MUST distinguish the sections accessibly. Done MUST contain completed tasks whose actual completion date equals the selected date; canceled tasks MUST remain Logbook-only. |
| LN-TASK-032 | Quick-create in an open daily section MUST write the selected plan date and matching `plan.at`. Its collapsed input row MUST retain visible separation after its bottom border before the first task card. Dragging within or between open sections MUST persist order, selected date, and day part. Dropping into Done MUST complete at the injected clock; dragging out of Done MUST reopen and reschedule to the selected date. Completion MAY remove a row when its actual completion date differs from the selected date. Existing rolling recurrence advancement MUST remain authoritative instead of creating completion-history rows. |
| LN-TASK-033 | Task summaries and catalog adapters MUST expose optional checklist total and completed counts without embedding checklist contents. A task row whose total is nonzero MUST finish with a checklist footer after its application and list chips. The footer MUST be the final child of the whole task card, span its full width below both the content and trailing controls, and retain both bottom corner radii. The body above that footer MUST have square lower corners, including while hovered. It MUST have a separating top border, a subtly darker semantic surface, a compact progress bar and count, and an independent disclosure that defaults collapsed and lazily loads its `TaskDocument`. The trailing task-details control MUST be vertically centered with the task title line, and the hover/focus drag handle MUST share the vertical center of that title line and its Tasks checkbox. Hovering the task body MUST NOT recolor the footer; its hover outline MUST instead frame the whole task card, including the footer. Hovering or focusing within the footer MUST use a separate footer-owned hover surface. Row, body, and opaque swipe-content surfaces MUST use the same hover timing so the title surface does not animate separately. When the row is selected, its selection surface MUST continue through the checklist footer; contiguous selected rows MUST square their joining body and footer corners so the selection outline does not leak at either side. Expanded items MUST use the public Tasks `ApplicationTaskCheckbox`, remain keyboard operable, and MUST NOT select, open, or drag the row. | LN-TASK-034 | Both `type: task` and `type: task-list` documents MUST be scanned with Markdown CST ranges. Structural candidates MUST be resolved through host link resolution and target front matter before becoming entries. Missing or non-Task targets MUST produce diagnostics and remain ordinary Markdown. Recognition MUST retain the authored label, href, target id/path, exact list-item range, nesting depth, heading path, and source order without altering source. |
| LN-TASK-035 | `TasksPlugin` MUST register one plugin-scoped `task-structure-runs` Markdown contribution without importing Lapis Markdown or Mira. Reading mode, embeds, and live preview MUST use one Tasks-owned rich TaskRun block for both Task and List documents. Source mode MUST reveal the original Markdown. Live preview MUST expose an explicit code-icon control that reveals the original TaskRun source; reading mode and embeds MUST omit that control. The live-preview control MUST overlay the run's inline end without consuming a standalone layout row, while body clicks and double-clicks remain owned by row interactions. It MUST be inset inside the trailing edge of its owning category pill and vertically centered with that heading. Task entries MUST reuse the rich task row and list entries MUST use task-row-aligned rows with a list icon, selection, disclosure, delete, drag, a hover/focus drag handle, and a trailing open control. Ordinary Markdown surfaces MUST omit planner-only creation, delete, drag, and drag-handle behavior; keep rich rows within the Markdown render width so both end radii remain visible; and preserve the dedicated Tasks checkbox and tick against host Markdown checkbox selectors. In reading mode and live preview, each H2-H6 that owns at least one resolved rich TaskRun, or at least one lightweight checklist item in a Task document, MUST retain its semantic heading while using the same pill-shaped category treatment as a Today section, including the workspace sans font family, size, weight, tracking, casing, and line height of the Today section label. Live-preview category lines MUST position their fold affordance immediately outside the pill's start border while keeping it vertically centered, and MUST vertically center source markers and the heading label within the pill instead of inheriting CodeMirror's top-aligned line contents. Owned headings MUST receive deterministic colours in source order by cycling through the Tasks neutral, warning, info, accent, and success roles; multiple runs under one heading MUST share one colour. Unowned headings, H1, implicit-root entries, and every heading in source mode MUST keep ordinary Markdown presentation. `task-list-navigation` presentation headings with resolved List rows MUST follow the same treatment without gaining structural ownership. TaskRuns and the daily planner MUST share the same quick-create presentation, whose collapsed label and retained draft label MUST use normal, non-bold weight. |
| LN-TASK-036 | The sortable unit MUST be one contiguous structural TaskRun, never an entire heading section. Reorder MUST remain within that run. Prose, headings, checkboxes, ordinary links, images, tables, code blocks, and unrelated list items MUST split or bound runs and MUST remain byte-for-byte stable. A cross-run or cross-heading drop MUST be an explicit structural move that removes and inserts exact item ranges, recalculates a relative href when the parent document changes, and reparses both affected documents. Active editable surfaces MUST dispatch CodeMirror changes rather than writing behind the editor; repository mutations MUST guard expected source before writing. |
| LN-TASK-037 | Selecting either a Task List or Task in the Tasks workspace MUST mount its real `TFile` through the public Markdown file-surface provider and show the complete document in source order. List pages MUST use Column Canvas pencil/book-open controls; task details MUST retain task metadata/action chrome while embedding the complete Markdown body with the same controls. A preview MUST hide the document H1 only when it matches the surrounding Column Canvas page title; edit mode MUST retain the H1 source. Linked-list open MUST use a closeable adjacent column with the same border, background, and radius treatment as the planner column. Leaving edit mode MUST flush first, save failure MUST retain the dirty editor, refresh MUST protect dirty buffers, and preview/edit MUST share the active Markdown theme with one vertical scroll owner. | LN-TASK-038 | H1 MUST remain the document display title and MUST NOT enter grouping context. H2–H6 headings MUST define derived `headingPath`, `headingLevel`, and `headingText` for following structural entries. Nested headings MUST extend the path; a same-or-shallower heading MUST close the prior context. Entries before the first H2 MUST use the implicit root group with an empty path and null heading text. Heading context MUST NOT be duplicated into front matter. |
| LN-TASK-039 | A TaskRun MUST be a maximal contiguous sequence of resolved structural list items with the same source list, nesting depth, and heading path. The disposable projection MUST store run ids/ranges/counts and entry kind, target, path, run position, and source ranges. Markdown order MUST remain authoritative. Deleting and rebuilding the projection from Markdown MUST reproduce the same relationships and ordering. |
| LN-TASK-040 | Whole-vault structural validation MUST report unresolved targets, unsupported target types, multiple structural parents, and cycles. Invalid candidates MUST stay visible as Markdown and MUST be omitted only from active structural edges. Navigation links MUST remain presentation-only even when they point to nested lists. |
| LN-TASK-041 | Tasks-owned surfaces MUST support reorder inside a TaskRun, explicit move to another run or heading, creation and rename of ordinary Markdown headings, adding a Task or nested List under a chosen heading, and recursive expand/collapse of linked Lists. Cross-run drag payloads MUST identify the source document, run, and position. A nested List disclosure MUST render that List's own heading-aware runs without changing structural ownership. Its guide MUST use `--interactive-accent` and resolve to Lapis `--ui-workspace-focus-ring` inside a Lapis Markdown surface. |
| LN-TASK-042 | Public structural APIs MUST expose target-resolved entry and run shapes without making the database authoritative. The published runtime MUST carry its Markdown CST parser dependencies portably, and every structural operation MUST be testable as a pure scan or exact editor change independently of Lapis Markdown and Mira. |
| LN-TASK-043 | Package Storybook MUST expose the host brand-theme picker and manager-level light/dark toggle. It MUST default to Lapis and light mode, apply the brand through `data-ui-theme`, and apply color mode through the preview document root's `dark` class without adding a competing background-theme decorator. Governed Obsidian-dark and Default-dark stories MUST assert that the preview root resolves `color-scheme: dark` and MUST measure the repaired Tasks surfaces in the real shell. | LN-TASK-044 | `task.repeat` MUST use rolling recurrence with required `frequency` `daily`, `weekly`, `monthly`, or `yearly`; positive numeric `interval` defaulting to `1`; and `anchor` `schedule` or `completion` defaulting to `schedule`. `on` MAY be retained as string-list metadata but MUST NOT affect current scheduling. Completing a recurring Task MUST keep it open, clear inbox and terminal completion state, advance an existing plan by one interval while preserving its other fields, record `lastCompletedAt`, increment `completionCount`, and reset every lightweight checklist marker only when `resetChecklist` is true. A recurring Task without a plan MUST NOT invent one.
